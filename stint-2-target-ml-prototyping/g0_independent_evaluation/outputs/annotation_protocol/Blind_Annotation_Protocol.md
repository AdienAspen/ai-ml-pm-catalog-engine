# G0.1 — Blind Annotation Protocol

**FSA BRIDGE / AI-ML Workstream · STINT_2 · Phase G0**
Version 1 · Applies to admitted denominator units only

---

## 1. Purpose

Produce the independent evaluation set for STINT_2.

All STINT_1 evidence carries `evaluation_independence: derived_from_rules`, generated by rule sets and by `paraphrase-multilingual-MiniLM-L12-v2`. A classifier evaluated against those labels measures itself against its own logic.

This protocol defines how a human annotator assigns labels **without seeing any pipeline output**, so that the resulting set is mechanistically independent of the systems being evaluated.

---

## 2. What makes this independent

Independence here is not about who annotates. It is about **what the annotator sees**.

```
pipeline mechanism    embedding similarity to a prototype,
                      or regex pattern match

annotation mechanism  human reads the text and assigns against
                      a written definition
```

Two different assignment mechanisms. Sharing the same reference vocabulary does not create circularity — **seeing the model's proposal would**.

| Condition | Registration |
|---|---|
| Annotator assigns without seeing any proposal | `independent` |
| Annotator confirms or rejects a shown proposal | `human_validated` |
| Label produced by rules or embeddings | `derived_from_rules` |

**Only `independent` records may enter the evaluation set.**

---

## 3. Declared limitations of the instrument

State these in every report that uses this set. They are limits, not defects to conceal.

- **No SME is available.** Annotators are ML practitioners, not wind turbine maintenance experts.
- **Annotators can judge information type.** Whether a text describes an observed condition, an action performed, or an administrative motive — this was validated in STINT_1 across 80 records.
- **Annotators cannot judge fine domain distinctions.** Whether a worn bearing maps to `C-045` or `C-047` requires domain expertise this project does not have.
- **Consequence:** the evaluation set is strong for targets where the distinction is one of information type, and weak where it demands fine catalogue discrimination.

---

## 4. Annotation task

### 4.1 What the annotator sees

```
SHOWN         annotation_id
              text, PII-redacted
              target being annotated
              the controlled response vocabulary for that target

NOT SHOWN     pipeline proposal · anchor · confidence score
              anchor_source · target_hint · tier · path
              any semantic flag or cue marker
              other annotators' responses
```

### 4.2 What the annotator returns

One response per record, from the target's controlled vocabulary, plus `abstain`.

**Free-text notes are optional and never substitute the response.**

### 4.3 Abstention

`abstain` is a legitimate response and must not be minimised. Use it when:

- the text is not interpretable
- the text carries no information relevant to the target
- the distinction required exceeds the annotator's competence

**A high abstention rate is a finding about the corpus, not a failure of the annotator.**

---

## 5. Per-target definitions

Definitions derive from the reference layer established in STINT_1.1. Sources are named per target.

---

### 5.1 Symptom

**Question:** *Does this text describe a condition observed before the intervention, or something else?*

**Sources:** ZEUS `detection symptom` category · WMEP failure effects (8 published terms)

| Response | Definition |
|---|---|
| `observed_condition` | A state, measurement, or anomaly registered before or at the point of intervention. Includes OEM alarm codes with condition descriptions, CMS alerts with severity, and technician observations of state. |
| `dispatch_motive` | Why the technician was sent. Planned inspection, scheduled replacement, upgrade, audit, testing, troubleshooting. Describes intended work, not observed state. |
| `ambiguous` | Names a component or location without declaring a condition or an action. |
| `not_interpretable` | Administrative content, system logs, fragments, identifiers alone. |
| `abstain` | Cannot decide within the annotator's competence. |

**Boundary examples** *(from STINT_1 blind rounds)*

```
observed_condition   temperature high on gearbox bearing, with measured value
                     water level too low, with alarm code
                     CMS alert with component and severity level
                     hydraulic pressure low
                     leak in hub

dispatch_motive      annual inspection
                     software release
                     blade replacement
                     reliability testing
                     weatherization checklist

ambiguous            chain hoist
                     smoke sensor
                     cooler motor

not_interpretable    part number only
                     time allocation correction
                     inventory adjustment
```

**Tie-break rules**

- A text containing both a condition and an action → classify by what **triggered** the work. `"yaw feedback error troubleshoot"` is `observed_condition`; the error came first.
- A text naming a component with a state adjective (`bad gen fan`) → `observed_condition`.
- A text naming a component alone (`gen fan`) → `ambiguous`.
- `"Missing Notification - [code][condition]"` → `ambiguous`. The condition is present but framed as an administrative gap.

---

### 5.2 Damage

**Question:** *Does this text describe a physical damage or degradation process?*

**Sources:** NREL Gearbox Reliability Database · per-subsystem failure mode vocabularies (blades, generator, pitch, yaw, converter, transformer, hydraulics, main bearing)

⚠️ **Critical distinction, established in DELTA-0008:** in SAP, Damage is the **physical process that led to failure**, not what was observed. `spalling`, `wear`, `cracking`, `corrosion` are damage. `high temperature` is a symptom, not a damage.

| Response | Definition |
|---|---|
| `damage_present` | Names a physical damage or degradation process affecting a component. |
| `symptom_not_damage` | Describes an observed state or measurement, not the physical process. |
| `action_not_damage` | Describes work performed, not a damage condition. |
| `not_interpretable` | No usable content. |
| `abstain` | Cannot decide. |

**Boundary examples**

```
damage_present       spalling on bearing race
                     seal leaking
                     cracked bushing
                     worn brush

symptom_not_damage   temperature high
                     vibration detected
                     low pressure

action_not_damage    replaced filter
                     cleaned belly
```

---

### 5.3 Cause

**Question:** *Does this text state why the failure or condition occurred?*

**Source:** WMEP failure causes (9 published categories)

⚠️ **Rule inherited from STINT_1 and non-negotiable:** never infer cause from damage. A damaged bearing does not state its cause. If the text does not say why, the answer is not `cause_present`.

| Response | Definition |
|---|---|
| `cause_present` | States a reason: wear, lubrication failure, grid event, lightning, icing, high wind, loosening of parts, control malfunction, external damage. |
| `no_cause_stated` | Describes condition, damage, or action without stating why. |
| `not_interpretable` | No usable content. |
| `abstain` | Cannot decide. |

---

### 5.4 Activity

**Question:** *Does this text describe maintenance work performed?*

**Source:** ZEUS `maintenance measure` category

| Response | Definition |
|---|---|
| `activity_present` | Names work performed or to be performed: replacement, repair, inspection, cleaning, adjustment, lubrication, troubleshooting. |
| `condition_not_activity` | Describes state, not work. |
| `not_interpretable` | No usable content. |
| `abstain` | Cannot decide. |

---

### 5.5 Object Part

**Question:** *Does this text identify a specific component that was affected or worked on?*

**Source:** wind turbine equipment taxonomy · IEC 61400-25-2 physical subsystem nodes · ISO 14224 hierarchy levels

⚠️ **Granularity note:** the reachable FLOC leaf is Component/Maintainable Item, not Part. A component more granular than the FLOC leaf has no node to land on. Annotate what the text says; the granularity ceiling is a downstream mapping concern.

| Response | Definition |
|---|---|
| `component_identified` | Names a specific physical component. |
| `system_only` | Names a system or subsystem without component-level specificity. |
| `no_component` | No component named. |
| `not_interpretable` | No usable content. |
| `abstain` | Cannot decide. |

MAT is resolved by direct field in the relational path, with 10,749 `real_observed_label` units. It is the only contractual denominator in the project and requires no proxy evaluation.

**If MAT modelling is later attempted on GE paths**, a separate protocol section is required.

## 6. Sampling rules

Implemented by the DevOps team. Stated here because they affect validity.

### 6.1 Admitted units only

Protocol v1 samples **only units admitted to the F6 proxy denominator**. G1 candidates — Object Part B1 (4,079) and FLOC leaf (10,749) — are excluded until admitted.

If G1.1 or G1.2 produce admissions, a **second annotation round** covers them. Mixing unadmitted candidates would contaminate the set before it exists.

### 6.2 Sampling unit

Sample by `sampling_unit_key`, not by `source_unit_key`.

**Rationale:** in `RELATIONAL_REASON`, 1,827 rows map to 696 distinct hashes — an average of 2.6 records per value. Sampling by unique value under-represents what the model will actually encounter.

⚠️ **Frequency cap:** no single `source_unit_key` may exceed **5% of a target's sample**. This prevents the failure observed in STINT_1, where one repeated value occupied 19 of 40 sampled rows and rendered the sample uninterpretable.

### 6.3 Stratification

Stratify each target's sample across:

```
path             PATH_A · B1_RELATIONAL · B2_WORKBOOKS
stratum          as declared in F6
anchor_source    domain_vocabulary vs sap_catalog
```

⚠️ **Do not sample by confidence band.** A set drawn from high-confidence rows inflates every downstream metric.

### 6.4 Target sizes and ceilings

```
target size      150–300 per target where evidence allows
ceiling rule     where admitted units < target size,
                 annotate all and declare the ceiling
```

**Known ceilings from G0.0:**

```
Cause · PATH_A            36 admitted → annotate all
Symptom · PATH_A_NOTES    42 admitted → annotate all
Symptom · B2_WORKBOOKS    62 admitted → annotate all
Symptom · PATH_A_CONCERN  68 admitted → annotate all
FLOC leaf                  0 admitted → excluded from v1
```

### 6.5 Never cross paths

Path namespaces are not comparable — `PHY-*`, `B25EVENT-*` and `PATHA-EVENT-*` count physical records, dated events and estimated events respectively. **Sample per path, report per path, never deduplicate across paths.**

## 7. Environment and handling

```
visible-text package    closed environment · permissions 600
                        not versioned · covered by .gitignore
responses returned      sampling_unit_key → response only
                        never the text itself
PII                     redacted before the package is produced
versioned artefacts     sanitized only · hashes and counts
```

**Ordering rule:** the annotator receives the package **before** any pipeline output for those records is generated or consulted. If a pipeline result already exists, the annotator must not see it.

---

## 8. Inter-annotator agreement

Where two annotators are available:

- Both annotate the same subset independently, without seeing each other's responses
- Report raw agreement and Cohen's kappa per target
- Disagreements are **not resolved by discussion into the evaluation set** — they are recorded as such

**Why this matters:** no one measures how much two reviewers agree on the same record in a multi-thousand-code catalogue. If human-human agreement is 0.70 and model-human agreement is 0.68, the model operates within the variability of the available standard. That reframes the accuracy question entirely.

**Register annotator identity per response.** In STINT_1, one round was `model_blind_review` and one was `human_blind_review`; both must remain distinguishable.

Every record entering the evaluation set carries:

```

target
path
response

                           semantic_prototype_matching_v1
                           paraphrase-multilingual-MiniLM-L12-v2
annotation_date
```

---

## 10. Exclusion from training

**Records in the evaluation set are removed from the training pool before any model is fitted.**

If a record is annotated and also used for training, the model learns from the same material it is measured against. This must be verified programmatically, not assumed.

---

## 11. Protocol change control

Any change to definitions, response vocabularies, or tie-break rules **after annotation has begun** invalidates comparability.

```
change required   →  new protocol version
                  →  re-annotate affected records
                  →  never retroactively reinterpret existing responses
```

Record the protocol version on every response.

---

## 12. What this protocol does not produce

- **Not ground truth.** These are annotations by non-SME reviewers, not client-validated mappings.
- **Not a contractual denominator.** The contractual denominator remains MAT only.
- **Not domain certification.** The set measures model behaviour against a written standard; it does not certify that the assigned SAP code is correct in the client's operational reality.

**It is an independently generated evaluation set with declared limitations — which is the strongest instrument available given the absence of SME access.**
